## 1. Удаление карточки из массива

### Вариант 1: `findIndex` + `splice`
```ts
const index = cards.findIndex(c => c.id === id);
if (index === -1) return res.status(404).json({ error: "Карточка не найдена" });
cards.splice(index, 1);
```
**Плюсы:** удаляет на месте, без создания копии массива, один вызов `splice`
**Минусы:** мутирует массив напрямую (но `cards` объявлен через `const`, а `const` блокирует только переназначение переменной, не сам массив)

### Вариант 2: `filter` с пересозданием массива
```ts
const index = cards.findIndex(c => c.id === id);
if (index === -1) return res.status(404).json({ error: "Карточка не найдена" });
const newCards = cards.filter(c => c.id !== id);
```
**Плюсы:** функциональный стиль, не мутирует исходный массив
**Минусы:** создаёт новый массив (копирует все элементы кроме одного), `cards` объявлен как `const` — для замены нужен `let`

### Выбранный вариант: `findIndex` + `splice`
Массив карточек небольшой (несколько элементов), `const` не мешает мутации — `splice` изменяет содержимое, но не переназначает переменную. Проще и эффективнее.

## 2. Обработчик неизвестных адресов

### Вариант 1: `app.use` без пути после всех роутов
```ts
app.use((req, res) => {
  res.status(404).json({ error: "Маршрут не найден" });
});
```
**Плюсы:** middleware без строки-пути срабатывает на любой маршрут; порядок в коде определяет приоритет — если поставить после всех роутов, сработает только когда ни один роут не вызвал `res.json()`/`res.send()`
**Минусы:** менее явный intent — читатель может не сразу понять, что это fallback

### Вариант 2: `app.all("*")`
```ts
app.all("*", (req, res) => {
  res.status(404).json({ error: "Маршрут не найден" });
});
```
**Плюсы:** явно говорит «любой метод, любой путь»
**Минусы:** `app.all` может конфликтовать с middleware-цепочкой Express, иногда перехватывает и обработанные маршруты если стоит не в том порядке

### Выбранный вариант: `app.use` без пути
Стандартная практика Express: middleware без строки-пути срабатывает после всех роутов. Порядок в коде определяет приоритет — это надёжнее и привычнее.

## 3. Обработчик ошибок

### Вариант 1: четыре параметра `(err, req, res, next)`
```ts
app.use((err, req, res, next) => {
  res.status(500).json({ error: "Внутренняя ошибка сервера" });
});
```
**Плюсы:** Express распознаёт функцию с четырьмя параметрами как error-handling middleware; `err` получает объект ошибки; порядок критичен — должен быть последним middleware
**Минусы:** функция с 4 параметрами не получает обычные `req`/`res` для нормальных запросов — только ошибки

### Вариант 2: два параметра `(req, res)` с ручным try/catch
```ts
app.use((req, res) => {
  // обработка ошибок вручную
});
```
**Плюсы:** получает все запросы
**Минусы:** не интегрируется с механизмом ошибок Express; каждый роут должен оборачиваться в try/catch; при пропуске `next(err)` ошибка теряется

### Выбранный вариант: четыре параметра `(err, req, res, next)`
Express использует количество параметров для определения типа middleware: 4 параметра = error-handling middleware. Это встроенный механизм Express.

**Почему порядок важен:** обработчик 404 должен идти перед error handler, иначе error handler перехватит и 404-ошибки. Error handler должен быть последним — иначе другие middleware перехватят ошибки до него.

## Порядок регистрации

```ts
app.use(express.json())           // парсинг JSON (строка 7)
app.get("/cards", ...)            // GET /cards (строка 15)
app.post("/cards", ...)           // POST /cards (строка 19)
app.delete("/cards/:id", ...)     // DELETE /cards/:id (новый)
app.use((req, res) => ...)       // 404 для неизвестных маршрутов (новый)
app.use((err, req, res, next) => // error handler (новый, последний)
app.listen(PORT, ...)            // запуск (строка 30)
```
