## 1. Подтверждение удаления

### Вариант 1: `window.confirm()`
Нативный блокирующий диалог браузера. Минимум кода, не требует управления состоянием в React, автоматически блокирует UI на время показа.

**Плюсы:**
- 2 строки кода, ноль лишнего состояния
- Нативная доступность и фокус-менеджмент
- Не требует оверлеев и стилей

**Минусы:**
- Стиль диалога зависит от ОС/браузера
- Блокирует поток выполнения

### Вариант 2: Кастомный диалог
Собственный компонент-оверлей с состоянием (`isOpen`, `cardIdToDelete`). Требует рендеринга модалки, управления фокусом, закрытия по Escape/клику вне области.

**Плюсы:**
- Полный контроль над дизайном
- Не блокирует поток

**Минусы:**
- Значительно больше кода и состояний
- Риск багов с закрытием/фокусом

### Выбранный вариант: `window.confirm()`
Достаточно для простой операции удаления. Не усложняет UI и архитектуру. Пользователь ожидает стандартное подтверждение для необратимого действия.

## 2. Расположение мутации и проброс коллбека

### Вариант 1: Props (`App` → `BoardColumn` → `BoardCard`)
`App` создаёт `useMutation` и `useQueryClient`, пробрасывает `onDelete(id)` вниз. `BoardColumn` передаёт коллбек и `card.id` в `BoardCard`.

**Плюсы:**
- Прозрачный поток данных, соответствует текущей архитектуре (`App` управляет данными)
- `invalidateQueries` живёт там же, где и `useQuery`
- Минимум скрытого состояния

**Минусы:**
- Проброс props через уровни (но глубина всего 3 уровня)

### Вариант 2: `useMutation` прямо в `BoardCard`
`BoardCard` сам делает запрос на удаление. `invalidateQueries` нужно пробрасывать через props или вызывать внутри компонента.

**Плюсы:**
- `BoardCard` самодостаточен

**Минусы:**
- Нарушает разделение ответственности: презентационный компонент управляет кэшем
- Сложно пробросить `queryClient` без пропса или контекста
- Дублирование логики инвалидации

### Вариант 3: Context
Создать `DeleteContext`, обернуть `App`, читать в `BoardCard`.

**Плюсы:**
- Не нужно пробрасывать props

**Минусы:**
- Избыточно для одного коллбека
- Скрывает зависимости, усложняет отладку

### Выбранный вариант: Props
Соответствует текущей архитектуре проекта. `App` держит данные и мутации, дочерние компоненты — презентационные. Проброс через 3 уровня допустим и читаем.

## 3. Обновление доски после удаления

### Вариант 1: `invalidateQueries({ queryKey: ["cards"] })`
Стандартный подход React Query. После успешного удаления кэш инвалидируется, происходит повторный `fetchCards()`, UI обновляется.

**Плюсы:**
- Синхронизация с сервером гарантирована
- При ошибке сервера запрос не инвалидируется → карточка остаётся на доске (требование спеки)
- Нет ручного управления состоянием

**Минусы:**
- Небольшая задержка до перезапроса данных

### Вариант 2: Оптимистичное обновление
Мгновенно убирает карточку из UI, при ошибке сервера требует отката состояния через `onError`.

**Плюсы:**
- Мгновенный отклик UI

**Минусы:**
- Требует ручного отката при ошибке
- Усложняет логику: нужно хранить предыдущее состояние, обрабатывать `onError`
- Риск рассинхронизации кэша и сервера

### Выбранный вариант: `invalidateQueries`
Проще и надёжнее. Автоматически обеспечивает требование спеки: при ошибке сервера карточка остаётся, так как кэш не меняется и запрос не перезапрашивается.

## Проверка ответа сервера в deleteCard

Функция `deleteCard` в `client/src/api/cards.ts` должна явно проверять `response.ok`. Если сервер вернул 4xx/5xx или произошла сетевая ошибка, `fetch` всё равно разрешит промис. Без проверки `response.ok` мутация завершится успешно, но карточка не удалится на сервере, что нарушит требование спеки о сохранении карточки при ошибке.

```ts
export async function deleteCard(id: string): Promise<void> {
  const response = await fetch(`/api/cards/${id}`, { method: "DELETE" });
  if (!response.ok) throw new Error("Не удалось удалить карточку");
}
```
